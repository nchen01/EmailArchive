# S39 - Recipient Handoff Project Grouping / Snapshot Coverage Labels

Status: implemented.

## Problem

The recipient package view groups its left rail with `frontend/src/utils/coverageAreas.ts`,
which clusters claims by shared evidence subjects and salient tokens because the
recipient snapshot carried no project labels. On a large, densely cross-referenced
package that clustering can merge everything into one area, so the recipient has to
read a wall of evidence to find one project. The creator side was fixed in S37 by
grouping with live project metadata, but the recipient view must never touch live
mailbox / project / event / message / L0 / L1 / L2 rows, so it needs the labels
frozen into the package itself.

## Decision

Freeze a project/coverage label onto each claim at generate time and group the
recipient rail by that frozen label. This is the smallest snapshot that makes real
project grouping possible while keeping the recipient strictly package-local.

## Snapshot shape

One nullable column, `handoff_claim.project_label TEXT`, populated in the same
generate transaction that writes the claims. The generator already runs on the
creator/coverer-owned mailbox, so it resolves `project_id -> label` once from that
mailbox's own `project` table (a permitted owner-side read) and stores the label on
the claim. The label is `NULL` when the claim has no `project_id` or the project has
no usable label.

Why the claim, not evidence or a new table:

- Evidence groups through the claim(s) that cite it, so a label on evidence would be
  redundant.
- A dedicated `handoff_coverage_area` table would add a table, a claim foreign key,
  a join, and more surface for the sake of server-side ordering and zero-claim areas
  that the recipient rail does not need. The recipient renders only areas that have
  claims and orders them deterministically on the client. The column is the minimal
  structure; the table stays available as a future option if per-area provenance or
  server-driven ordering is ever required.

## Data flow

1. `services/db/models.py`: `HandoffClaim.project_label` (nullable Text).
2. Migration `0014_handoff_claim_project_label` (down_revision `0013_return_handoff`):
   `ALTER TABLE handoff_claim ADD COLUMN IF NOT EXISTS project_label text;`
   Downgrade drops the column. Additive, no backfill, service-DB only, so
   `SCHEMA_VERSION` is not bumped (the handoff DTOs live in `services/api/schemas`,
   not `packages/ekc_schemas`).
3. `services/handoff/generator.py`: `_project_labels()` resolves labels from the
   owner mailbox's `project` table; `generate_candidate` freezes each claim's label.
4. `services/api/schemas/handoff.py`: `RecipientClaimOut.project_label: str | None`.
5. `services/api/routers/handoff_recipient.py`: surfaces `c.project_label`. The
   route still reads only `handoff_claim` and `handoff_evidence` rows.
6. Frontend: `frontend/src/utils/recipientGroups.ts::buildRecipientAreas` selects the
   grouping; `RecipientPackage.tsx` uses it instead of `buildCoverageAreas`.

## Grouping and degradation (frontend)

`buildRecipientAreas(claims, evidence)` returns `CoverageArea[]` (the shape the rail
already renders), derived purely from the package payload:

- No claim carries a label (pre-S39 package): fall back to the existing
  `buildCoverageAreas` clustering, unchanged.
- Labeled claims group by their frozen label.
- Unlabeled claims in a mixed package are not dumped into one giant bucket: they run
  through `buildCoverageAreas`; if that yields two or more useful areas they are
  kept, otherwise they collapse into one honest "Other coverage" bucket.

## Creator behavior

Unchanged. The creator review keeps the S37 live-project-metadata grouping. The new
column is written at generate but the creator DTO is not modified.

## Return handoffs

Return (`return_delta`) packages are generated by the same `generate_candidate`, so
their claims freeze the coverer-side project label the same way and group cleanly.
`handoff_return_context.carried_area_labels` remains available for the "what changed
while you were away" framing.

## Invariants

- Recipient stays snapshot-only: no new live query is added; the route reads only
  `handoff_*` rows. Labels are frozen, never re-resolved.
- One-time link, session exchange, and expiry/revoke behavior are untouched.
- No Gmail/source link, source header, mailbox id, token, or vault ref is introduced.
- Sensitivity/noise/exclusion gates are unchanged: a label is only ever frozen onto a
  claim that already passed the safe-header and citation gates, and no label is
  emitted for a project that produced no surviving claim, so a label cannot act as an
  existence oracle for excluded content.
- Admin/Audit is unchanged: no admin DTO gains `project_label`; per-claim labels are
  not exposed in Admin/Audit.

## Tests

Backend (DB-gated, `tests/test_s39_recipient_project_grouping.py`): generate freezes
the expected labels on claim rows; the recipient payload returns `project_label`;
labels are unchanged after live `project` rows are renamed and deleted; the recipient
package still renders after every Project/Event/Message/Thread row is wiped (proving
snapshot-only); a claim with no project yields a null label; an excluded whole-thread
project contributes no label and none of its content/headers leak; a `return_delta`
package freezes coverer-side labels. Existing S17 / S34 / S29 / S30 suites continue to
pass. Frontend grouping branching was validated with a standalone node mirror of
`buildRecipientAreas` (labeled grouping, no-label fallback, mixed keep-vs-collapse),
since the repo has no frontend test runner.
